Is the race acceptable?
Yes, it is practically acceptable because:
1. Eager loading via `appScope?.launch { syncCookieStoreForProfile(id) }` happens extremely early during application initialization (before any UI is even drawn, since `AuthManager` is initialized before the first Activity).
2. The UI rendering lifecycle, Compose recomposition, and ViewModel `init` block execution naturally introduces a delay that is usually longer than the ~10-20ms required to load the cookies from `EncryptedSharedPreferences`.
3. Even if a race occurs on a severely constrained device during a cold start, the app handles network failures with retry mechanisms (like `safeApiCall`'s backoff for timeouts/5xx, though maybe not for 401s). But wait, does it retry 401s? No.
4. If a 401 occurs due to this specific race, the user will be prompted to log in again, which is a rare edge case on extreme cold starts.

What if we just use a `CountDownLatch` in `PersistentCookieJar` instead of `runBlocking`?
If `PersistentCookieJar.ensureLoaded` uses a latch, then `loadForRequest` can just do `latch.await()`.
This blocks the OkHttp thread (which is perfectly fine, it's a background thread!) but WITHOUT the heavy `kotlinx.coroutines.runBlocking` overhead!
```kotlin
    private val scopeLatches = ConcurrentHashMap<String, CountDownLatch>()

    // In useStore:
    suspend fun useStore(serverId: String) {
        scopeMutex.withLock {
            currentServerId.set(serverId)
            val latch = scopeLatches.getOrPut(serverId) { CountDownLatch(1) }
            if (latch.count == 0L) return
            try {
               ensureLoaded(serverId)
            } finally {
               latch.countDown()
            }
        }
    }
```
